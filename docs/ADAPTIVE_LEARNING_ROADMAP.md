# Adaptive learning implementation roadmap

This roadmap tracks working behavior, not just the presence of screens. Preserve existing uncommitted work.

1. **Classroom foundation:** verify teacher-owned classrooms, join codes, pending approval, active enrollment, access control and multiple memberships. Remove fabricated dashboard data. Make class subject and grade explicit and migrate existing data safely.
2. **Class diagnostic:** offer start or skip on entry per enrollment; persist the choice, a resumable 20-question session (15 + 5), answers and class/subject-specific baseline mastery. Define the purpose of the extra five questions and handle insufficient published questions without inventing results.
3. **Adaptive learning:** persist class-scoped attempts and mastery; select published content by grade, subject, topic and demonstrated mastery; adjust difficulty with evidence and allow teacher-authored content. Supply sufficient reviewed curriculum and questions for classes 6–10.
4. **Progress and rewards:** add an idempotent server-side XP ledger, level thresholds, topic completion and badge awards, chapter completion and certificates, and India-time activity dates, streaks and calendar. Derive dashboard displays from persisted records.
5. **Leaderboard and assignments:** rank active members by the agreed XP scope; make assignments available to enrolled students and record submissions and completion. Support multiple classrooms without mixing context.
6. **Teacher insights:** provide classroom-authorized, real-data heatmaps and topic/chapter drilldowns, content management and assignment workflows, including meaningful empty states.
7. **End-to-end readiness:** migrations and import process for real reviewed content; authorization, concurrency and idempotency tests; teacher/student browser journeys and accessibility checks. Verify against the configured database before deployment.

## Current implementation and remaining work

- Active classroom enrollment gates class content, diagnostic sessions, awards, assignments, and class-specific mastery. Classroom attempts determine classroom XP; legacy attempts and mastery without a classroom remain unassigned.
- The teacher heatmap and student profile distinguish unassessed skills from assessed skills needing support; gap clusters omit students without assessment evidence. The CSV export uses the same distinction. Aggregate mastery averages use assessed records rather than treating missing records as zero.
- Diagnostics save the current session and answers in the database, resume per classroom, and require 20 published questions. The first 15 questions sample the curriculum; the final five prioritize weaker assessed skills with fresh questions where available.
- Teachers can create and edit classroom questions and lessons. Lessons are selected from available difficulty levels using the student's class-specific mastery. Private questions are scoped to the classroom; shared questions are editable by administrators.
- Skill badges and chapter certificate records are awarded at mastery >= 0.95 with at least three class-attributed attempts per skill. Assignment completion uses the same mastery threshold and three attempts per assigned skill after assignment creation. These thresholds are implementation choices requiring educator review.
- Generated question templates are saved as drafts requiring review; existing content is not overwritten. A sufficiently reviewed question and lesson bank is not yet available for all classes and subjects.
- The administrator review queue edits and publishes real questions. Shared curriculum imports use a server-side dry run and are restricted to administrators; teachers manage classroom-specific content. The old fabricated question editor, import success, skill graph fallback, and evaluation metrics have been removed.
- Migrations 0004–0012 have been prepared, and tested against the current PostgreSQL database inside a transaction that was rolled back. They have not been deployed. Migration 0009 puts legacy custom questions into draft because their classroom is unknown; migration 0010 preserves old mastery as unscoped instead of guessing a class. Migration 0012 places exact matches for known generic templates into review, preserving their previous status for a guarded downgrade.
- Remaining work includes reviewing and importing content, auditing remaining demo/profile fallbacks, richer assignment submissions, comprehensive browser journeys and accessibility checks, production-like migration testing, and a durable XP ledger if rewards must extend beyond attempt-derived XP.

Content audit: the curriculum data lists 25 grade/subject combinations and 639 skills, but only one skill name matches the explicitly curated question registry. An audit of the configured database identified 1,914 published generic-template questions. The migration would put those questions into review, leaving enough published questions for the 20-question diagnostic in 2 of 25 subjects until educators review more. The administrator review queue loads, edits and publishes real database questions; review itself requires human subject expertise.

Legacy attribution: production contains 9,597 mastery records and 2,827 attempts without reliable classroom identifiers. They are preserved, but do not appear in class-specific dashboards; inferred attribution would be speculative. Applying migrations is a separate production change from the rollback-only test.

Security review: public student and teacher profile directories are restricted to administrators, and arbitrary profile fallbacks have been removed. The prior password-reset endpoint allowed password changes without proving email ownership; it now returns an unavailable error until verified token-based recovery is implemented. This is an outstanding feature, not a working recovery flow.

Verification: 234 API tests pass against the SQLite test database, but the full pytest command fails its configured 85% coverage gate (78.79% measured). Backend mypy and Ruff pass; 71 web unit tests, 14 API-client tests, and frontend TypeScript pass. The browser tests already in the repository intercept API requests and therefore do not verify a real end-to-end database journey. Practice submissions currently require a connection because the previous offline correctness calculation guessed the answer; queued offline grading still needs a truthful pending/sync design.
